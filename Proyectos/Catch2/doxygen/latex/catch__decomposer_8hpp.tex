\doxysubsection{Detailed Description}
Why does decomposing look the way it does\+:

Conceptually, decomposing is simple. We change {\ttfamily REQUIRE( a == b )} into {\ttfamily Decomposer\{\} \texorpdfstring{$<$}{<}= a == b}, so that {\ttfamily Decomposer\{\} \texorpdfstring{$<$}{<}= a} is evaluated first, and our custom operator is used for {\ttfamily a == b}, because {\ttfamily a} is transformed into {\ttfamily Expr\+Lhs\texorpdfstring{$<$}{<}T\&\texorpdfstring{$>$}{>}} and then into {\ttfamily Binary\+Expr\texorpdfstring{$<$}{<}T\&, U\&\texorpdfstring{$>$}{>}}.

In practice, decomposing ends up a mess, because we have to support various fun things.

1) Types that are only comparable with literal 0, and they do this by comparing against a magic type with pointer constructor and deleted other constructors. Example\+: {\ttfamily REQUIRE((a \texorpdfstring{$<$}{<}=\texorpdfstring{$>$}{>} b) == 0)} in libstdc++

2) Types that are only comparable with literal 0, and they do this by comparing against a magic type with consteval integer constructor. Example\+: {\ttfamily REQUIRE((a \texorpdfstring{$<$}{<}=\texorpdfstring{$>$}{>} b) == 0)} in current MSVC STL.

3) Types that have no linkage, and so we cannot form a reference to them. Example\+: some implementations of traits.

4) Starting with C++20, when the compiler sees {\ttfamily a == b}, it also uses {\ttfamily b == a} when constructing the overload set. For us this means that when the compiler handles {\ttfamily Expr\+Lhs\texorpdfstring{$<$}{<}T\texorpdfstring{$>$}{>} == b}, it also tries to resolve the overload set for {\ttfamily b == Expr\+Lhs\texorpdfstring{$<$}{<}T\texorpdfstring{$>$}{>}}.

To accommodate these use cases, decomposer ended up rather complex.

1) These types are handled by adding SFINAE overloads to our comparison operators, checking whether {\ttfamily T == U} are comparable with the given operator, and if not, whether T (or U) are comparable with literal 0. If yes, the overload compares T (or U) with 0 literal inline in the definition.

Note that for extra correctness, we check that the other type is either an {\ttfamily int} (literal 0 is captured as {\ttfamily int} by templates), or a {\ttfamily long} (some platforms use 0L for {\ttfamily NULL} and we want to support that for pointer comparisons).

2) For these types, {\ttfamily is\+\_\+foo\+\_\+comparable\texorpdfstring{$<$}{<}T, int\texorpdfstring{$>$}{>}} is true, but letting them fall into the overload that actually does {\ttfamily T == int} causes compilation error. Handling them requires that the decomposition is {\ttfamily constexpr}, so that P2564\+R3 applies and the {\ttfamily consteval} from their accompanying magic type is propagated through the {\ttfamily constexpr} call stack.

However this is not enough to handle these types automatically, because our default is to capture types by reference, to avoid runtime copies. While these references cannot become dangling, they outlive the constexpr context and thus the default capture path cannot be actually constexpr.

The solution is to capture these types by value, by explicitly specializing {\ttfamily \doxylink{structCatch_1_1capture__by__value}{Catch\+::capture\+\_\+by\+\_\+value}} for them. Catch2 provides specialization for {\ttfamily std\+::foo\+\_\+ordering}s, but users can specialize the trait for their own types as well.

3) If a type has no linkage, we also cannot capture it by reference. The solution is once again to capture them by value. We handle the common cases by using {\ttfamily std\+::is\+\_\+arithmetic} and {\ttfamily std\+::is\+\_\+enum} as the default for {\ttfamily \doxylink{structCatch_1_1capture__by__value}{Catch\+::capture\+\_\+by\+\_\+value}}, but that is only a some-\/effort heuristic. These combine to capture all possible bitfield bases, and also some trait-\/like types. As with 2), users can specialize {\ttfamily capture\+\_\+by\+\_\+value} for their own types as needed.

4) To support C++20 and make the SFINAE on our decomposing operators work, the SFINAE has to happen in return type, rather than in a template type. This is due to our use of logical type traits ({\ttfamily conjunction}/{\ttfamily disjunction}/{\ttfamily negation}), that we use to workaround an issue in older (9-\/) versions of GCC. I still blame C++20 for this, because without the comparison order switching, the logical traits could still be used in template type.

There are also other side concerns, e.\+g. supporting both {\ttfamily \doxylink{catch__test__macros_8hpp_ad57835ba8f1bb419a865ada6bd011a85}{REQUIRE(a)}} and {\ttfamily REQUIRE(a == b)}, or making {\ttfamily \doxylink{catch__matchers_8hpp_ac1354db6f3e9c1e0a8eda0eea7ff1f0a}{REQUIRE\+\_\+\+THAT(a, Is\+Equal(b))}} slot nicely into the same expression handling logic, but these are rather straightforward and add only a bit of complexity (e.\+g. common base class for decomposed expressions).
